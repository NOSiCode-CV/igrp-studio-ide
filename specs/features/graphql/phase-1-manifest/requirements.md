# Phase 1: GraphQL Manifest Requirements

## Objective

Implement a GraphQL manifest system per iGRP module.

The manifest defines the module-level GraphQL contract that future UI, validation, persistence, and generator flows will use. It must be the source of truth for GraphQL operations and must fit the existing iGRP Studio pattern where visual configuration is saved as JSON and later consumed by an engine/generator.

## Scope

### Manifest Structure

Define a `graphql.json` file that represents GraphQL configuration for one module.

The manifest must include:

- artifact type identifier
- module identifier
- optional manifest version
- operations list

Conceptual shape:

```json
{
  "type": "graphql",
  "version": 1,
  "module": "catalogo",
  "operations": []
}
```

### Supported Operations

The manifest must support:

- Query
- Mutation
- Subscription

Each operation must declare its GraphQL operation type explicitly.

### Operation Fields

Each operation can include:

- `id`
- `operationType`
- `name`
- `comment`
- `args`
- `inputType`
- `returnType`
- `returnMode`
- `eventTopic`

Operation field usage:

- `id` is required for all persisted operations.
- `id` is generated by the Main service/persistence layer, unique within the manifest, and stable even if `name` changes.
- `name` is required for all operations.
- `name` is the GraphQL operation name, not the technical identifier.
- `comment` is optional for all operations.
- `args` is optional but must be an array when present.
- `returnType` is required for all operations.
- `returnMode` is required for all operations.
- `inputType` is required for mutations.
- `eventTopic` is required for subscriptions.

### Argument Structure

Each argument must describe a GraphQL operation parameter.

Required argument fields:

- `name`
- `type`
- `required`

Optional argument fields:

- `defaultValue`
- `description`

Conceptual shape:

```json
{
  "name": "id",
  "type": "ID",
  "required": true,
  "defaultValue": null,
  "description": "Entity identifier"
}
```

### Type References

The manifest must allow GraphQL operations to reference return types, input types, and argument types by name.

`returnType`, `inputType`, and argument `type` are stored as string names. Full resolution against iGRP DTOs, schemas, generated GraphQL types, or supported scalar types is handled by Phase 3 validation and integration flows. Phase 1 defines structural validation, the manifest contract, and base persistence expectations only.

Supported scalar names for the base contract:

- `ID`
- `String`
- `Int`
- `Float`
- `Boolean`

Custom type references must be stored as names and resolved by Phase 3 reference validation.

### Return Modes

The manifest must define output cardinality through `returnMode`.

`returnMode` is a UI-level abstraction stored in the manifest. Future generator work will translate it into GraphQL single-object or list output syntax.

Required base modes:

- `single`
- `list`

### Module-Level Storage

The manifest must be stored per module, using the iGRP module structure.

Phase 1 freezes the target location as:

```txt
igrpstudio/<module>/graphql/graphql.json
```

The manifest belongs to one module and must not mix operations from different modules.

### Base Validation Rules

The manifest system must validate:

- manifest type must be `graphql`
- module must be present
- persisted operation `id` must be present
- operation IDs must be unique within the module manifest
- operation names must be unique within the module manifest
- operation name must be present
- operation type must be lowercase and one of `query`, `mutation`, or `subscription`
- argument names must be unique within the operation
- `returnType` must be present and syntactically valid
- `returnMode` must be one of `single` or `list`
- mutation must include `inputType`
- subscription must include `eventTopic`
- REST-only fields must not be accepted
- validation must run before file writes
- invalid manifests must never be partially written

## Out of Scope

- Renderer UI mapping
- GraphQL overview screens
- Query, Mutation, or Subscription form implementation
- Schema generation
- Resolver generation
- Spring Boot code generation
- Advanced GraphQL directives
- Federation
- GraphQL interfaces and unions
- Nested writes
- Authorization policy modeling
- Runtime execution of GraphQL operations

## Constraints

- JSON is the source of truth.
- The manifest must align with the existing iGRP module structure.
- The manifest must be compatible with future generator consumption.
- The manifest must not introduce REST concepts such as HTTP status codes, headers, content types, or REST bodies.
- The manifest must support future integration with existing DTOs and schemas without forcing GraphQL to become a REST DTO copy.
- Phase 1 must define only the contract and persistence expectations.
