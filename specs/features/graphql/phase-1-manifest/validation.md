# Phase 1: GraphQL Manifest Validation

## Automated Validation

Automated validation succeeds when the manifest contract can be represented consistently in the project type system and structurally validated before persistence.

Checks:

- TypeScript types are valid if implementation introduces manifest interfaces or schemas.
- Manifest top-level fields are consistent: `type`, `version`, `module`, and `operations`.
- Persisted operation `id` is required, generated by the Main service/persistence layer, stable across renames, and unique within the manifest.
- Operation model accepts only lowercase `query`, `mutation`, and `subscription`.
- Return modes accept only `single` and `list`.
- Argument model consistently supports `name`, `type`, `required`, `defaultValue`, and `description`.
- Manifest validation rejects unsupported REST-only fields.
- Validation errors are structured with at least a target field, message or reason, and error code or category.
- Invalid manifests are rejected before file write.
- Persistence only happens after successful validation, with no partial writes.

Expected result:

- A valid manifest can be parsed, validated, and written without changing unrelated project files.
- An invalid manifest produces validation errors and is not persisted.

## Manual Validation

Manual validation succeeds when a module-level `graphql.json` can be created, edited, read, and validated according to the Phase 1 contract.

### Create a Query Operation

Given a module named `catalogo`, create a manifest at:

```txt
igrpstudio/catalogo/graphql/graphql.json
```

With:

```json
{
  "type": "graphql",
  "version": 1,
  "module": "catalogo",
  "operations": [
    {
      "operationType": "query",
      "id": "op_get_carro_001",
      "name": "getCarro",
      "comment": "Busca carro por ID",
      "args": [
        {
          "name": "id",
          "type": "ID",
          "required": true
        }
      ],
      "returnType": "Carro",
      "returnMode": "single"
    }
  ]
}
```

Expected result:

- JSON is saved in the module GraphQL path.
- The operation is accepted as a valid query.

### Preserve Operation ID on Rename

Rename an operation by changing `name` while keeping the same `id`.

Expected result:

- Validation accepts the operation when the new name is valid and unique.
- Update and delete flows still target the operation by `id`.

### Reject Duplicate Operation Names

Add two operations with the same `name` in the same manifest.

Expected result:

- Validation rejects the manifest.
- No partially valid version is persisted.

### Reject Missing or Duplicate Operation IDs

Create persisted operations with a missing `id` or with duplicate `id` values.

Expected result:

- Validation rejects the manifest.
- The error identifies `id` as missing or duplicated.

### Reject Invalid Return Type

Create an operation with an empty, missing, or syntactically invalid `returnType`.

Expected result:

- Validation rejects the operation.
- The error identifies `returnType` as the cause.

### Reject Invalid Return Mode

Create an operation with a `returnMode` other than `single` or `list`.

Expected result:

- Validation rejects the operation.
- The error identifies `returnMode` as unsupported.

### Reject Mutation Without Input Type

Create a mutation without `inputType`.

Expected result:

- Validation rejects the mutation.
- The error identifies `inputType` as required for mutations.

### Reject Subscription Without Event Topic

Create a subscription without `eventTopic`.

Expected result:

- Validation rejects the subscription.
- The error identifies `eventTopic` as required for subscriptions.

### Reject Duplicate Argument Names

Create one operation with two arguments using the same `name`.

Expected result:

- Validation rejects the operation.
- The error identifies duplicate argument names.

### Reject REST Concepts

Add REST-only fields such as `statusCode`, `headers`, `contentType`, or `body`.

Expected result:

- Validation rejects the manifest.
- The error identifies unsupported REST modeling fields.
